## Что делает пакет

Telegram общается со своими дата-центрами по TCP на адреса из нескольких подсетей. Во многих сетях
это соединение медленное или заблокировано, а доступ к самому Telegram при этом возможен через
WebSocket на веб-эндпоинты `kws*.web.telegram.org`: тот же поток, но упакованный в обычный HTTPS.

Пакет делает эту упаковку **на роутере и прозрачно**:

1. Правило `nftables` перенаправляет соединения устройств домашней сети к подсетям Telegram на
   локальный демон `tgws`.
2. Демон определяет дата-центр, открывает WebSocket к Telegram и перекладывает поток туда и обратно.
3. Если WebSocket не сработал, байты клиента **дословно** повторяются прямым соединением,
   поэтому Telegram не ломается.

На телефонах и компьютерах ничего настраивать не нужно: ни прокси, ни secret, ни ссылку `tg://proxy`.

**Что видит роутер.** Демон снимает и накладывает только транспортную обфускацию соединения
(obfuscated2). Сообщения Telegram остаются зашифрованными его собственным протоколом MTProto от
клиента до сервера, и роутер их не читает.

## Установка

Нужны:

- роутер с **OpenWrt 25.12 или новее**, LuCI и пакетным менеджером `apk`;
- доступ по SSH и около 5 МБ свободного места (бинарник демона занимает 4–5 МБ);
- поддерживаемая архитектура (см. ниже).

OpenWrt 24.10 и более ранние версии с `opkg` не поддерживаются.

Выполните по SSH **на роутере**:

```sh
sh -c "$(wget -O - https://raw.githubusercontent.com/NooBiToo/tgws-openwrt/main/install.sh)"
```

Установщик:

1. проверяет версию OpenWrt и архитектуру **до** любых изменений;
2. ставит зависимости `curl`, `ca-bundle`, `firewall4`;
3. скачивает последний релиз и проверяет, что места достаточно (с запасом на две копии бинарника);
4. останавливает работающую службу, кладёт бинарник `/usr/bin/tgws` **до** установки пакета
   (иначе пакет запустил бы старый демон), ставит пакет `luci-app-tgws` и русский перевод;
5. перезапускает бэкенд LuCI и службу, если она работала.

После установки служба выключена. Откройте **Службы → Telegram → Настройки**, включите ускорение
и нажмите **Сохранить и применить**.

### Какие роутеры поддерживаются

Бинарник собирается под пять вариантов; установщик выбирает нужный по `DISTRIB_ARCH` из
`/etc/openwrt_release` (а не по `uname -m`: на mips ядро отвечает `mips` и для big-, и для
little-endian, а бинарнику порядок байт важен).

| `DISTRIB_ARCH` | Файл релиза | Примеры устройств |
|---|---|---|
| `x86_64` | `tgws-linux-x86_64` | x86-роутеры, виртуальные машины |
| `aarch64_*` | `tgws-linux-aarch64` | MediaTek Filogic, Rockchip, Raspberry Pi 3/4, Cudy, Xiaomi AX |
| `arm_*` | `tgws-linux-arm` | Cortex-A7/A9/A53 в 32-битном режиме, в том числе без FPU |
| `mipsel_*` | `tgws-linux-mipsel` | MT7621 и другие little-endian mips |
| `mips_*` | `tgws-linux-mips` | Atheros/QCA big-endian mips |

Для `arm` и `mips` бинарник собран с программной плавающей точкой: он работает и на устройствах без
FPU (BCM53xx, часть Atheros). Другие архитектуры (`mips64`, `riscv64`, `powerpc`) установщик
отклоняет до установки чего бы то ни было.

Если в 8–16 МБ флеша бинарник не помещается, установщик остановится с понятным сообщением, а не
оставит обрезанный файл.

### Диагностика

![Диагностика tgws в LuCI: проверки с подсказками и тест связи с таймингами по каждому адресу](Screenshot_2.png)

Страница нужна, чтобы отвечать на вопрос «почему не работает» без чтения исходников. Всё запускается
**кнопками**, потому что часть проверок ходит в сеть и занимает несколько секунд.

**Проверки** идут от настроек до настоящего запроса к Telegram и разбиты на четыре группы.

- **Служба:** демон установлен, ускорение включено, служба работает, демон принимает соединения.
- **Сеть:** правила перехвата загружены, интерфейсы локальной сети существуют, **зона файрвола
  принимает соединения к роутеру**, в локальной сети нет IPv6.
- **Telegram:** отвечает ли Telegram по WebSocket для каждого дата-центра из настроек (**настоящий
  запрос**, а не проверка порта), доступен ли Telegram напрямую, актуален ли список подсетей, нет ли
  адресов без известного дата-центра, идут ли соединения через WebSocket вообще.
- **Совместная работа с TrustTunnel:** не маршрутизирует ли он Telegram сам, и есть ли правило
  маршрутизации для метки, если она задана.

У каждой проверки есть вердикт (**ок / проверить / проблема / пропущено**), а у проблемных —
подсказка, что делать. Сначала показываются проблемы, пройденные проверки сворачиваются.

**Проверка связи** отправляет настоящий запрос в каждый дата-центр так же, как это делает демон, и
показывает по каждому адресу: ответил ли он, за сколько миллисекунд и какая была ошибка. Домены
одного дата-центра пробуются по порядку и только до первого ответившего: так же ведёт себя сам демон,
а лишнее соединение к тому же адресу может попасть под ограничение провайдера и дать ложный отказ.

Запускайте проверки и тест связи **по очереди**, не одновременно: частые параллельные соединения к
одному адресу в некоторых сетях ограничиваются.

## Как это работает внутри

### Перехват

Правила живут в **своей таблице `inet tgws`**, отдельной от таблиц других пакетов:

```
table inet tgws {
    set tg_v4 { type ipv4_addr; flags interval; auto-merge; elements = { ... } }
    chain intercept {
        type nat hook prerouting priority dstnat; policy accept;
        iifname != { "br-lan" } return
        ip daddr @tg_v4 tcp dport { 80, 443, 5222 } redirect to :5454
    }
}
```

- Перехватывается только **IPv4** и только TCP на портах 80, 443 и 5222.
- Только трафик, пришедший с **интерфейсов локальной сети** (по умолчанию устройство сети `lan`).
- Подсети Telegram берутся из списка, который обновляется раз в неделю (см. ниже); если обновить не
  удалось, используется зашитый список.
- Имя цепочки `intercept`, а не `redirect`: `redirect` — зарезервированное слово `nft`.

Перенаправленное соединение приходит к демону с адресом роутера, а исходный адрес назначения демон
узнаёт через `SO_ORIGINAL_DST`.

**Таблица загружается только после того, как демон начал слушать порт**, и снимается **первой**
при остановке. Поэтому не бывает момента, когда соединения перенаправлены в закрытый порт.
Готовность демон сообщает файлом счётчиков `/var/run/tgws.json`: он пишется сразу после `bind` и
удаляется при остановке до закрытия порта.

Команды `/etc/init.d/firewall start`, `reload` и `restart` таблицу `inet tgws` **не трогают**. А вот
`/etc/init.d/firewall stop` снимает **все** таблицы `nftables`, включая нашу; после этого
перехвата нет, и его возвращает `/etc/init.d/tgws restart` (страница «Состояние» подскажет это).

### Что говорит клиент

Первые байты соединения демон разбирает так:

| Что пришло | Что это | Что делает демон |
|---|---|---|
| `0xef` | открытый транспорт abridged | DC определяется по адресу назначения |
| `eeeeeeee`, `dddddddd` | открытый intermediate / padded | то же |
| 64 байта, расшифровавшиеся как obfuscated2 | клиент с обфускацией без прокси | DC берётся из заголовка, если он осмысленный |
| начало метода HTTP (`GET `, `POST` …) | обычный HTTP | сразу пропускается напрямую, без ожидания |
| что-то другое (например, TLS ClientHello) | не MTProto | пропускается напрямую, байты повторяются дословно |

**Android в прямом соединении пишет в заголовок мусорный индекс дата-центра** (ему он не нужен: он
подключается к конкретному адресу). Поэтому для Android дата-центр определяется по адресу, а не по
заголовку. Desktop индекс пишет правильно.

### Как определяется дата-центр

По порядку, пока не найден ответ:

1. **Ручное соответствие** `ip_dc` из настроек.
2. **Индекс из заголовка клиента**, если это допустимый номер (1–5 или 203).
3. **Зашитая таблица адресов.** В неё входят только адреса, в принадлежности которых есть
   уверенность (шесть адресов из upstream и три адреса, подтверждённых живой проверкой). Подсети не
   угадываются: ошибка в дата-центре ломает вход в аккаунт сильнее, чем отказ от ускорения.
4. **Выученное перебором.** Для неизвестного адреса демон читает первый пакет клиента и по очереди
   отправляет его на дата-центры, у которых есть цель WebSocket. Транспортная ошибка **`-404`**
   (ключ клиента неизвестен) или **`-444`** означает «не тот дата-центр», тогда пробуется следующий.
   Первый, кто ответил по существу, запоминается для этого адреса.

Если ни один не подошёл, соединение уходит в откат с дословным повтором всех прочитанных байтов.

Перебор надёжен на **авторизованных** сессиях. Первый незашифрованный запрос обмена ключами
(`req_pq`) принимает любой дата-центр, поэтому для совсем нового клиента перебор «выучит» первый
ответивший. Это согласованно, пока демон помнит выбор; после перезапуска первый же авторизованный
пакет уточнит его через `-404`.

### WebSocket и откат

WebSocket открывается на IP дата-центра (по умолчанию `149.154.167.220` для DC2 и DC4) с SNI и
заголовком `Host` вида `kws{N}.web.telegram.org` и путём `/apiws`. Затем демон строит собственный
obfuscated2-заголовок для стороны Telegram и перешифровывает поток AES-CTR в обе стороны,
разбивая исходящий поток на транспортные пакеты (по одному на кадр WebSocket).

Домены одного дата-центра пробуются по порядку: `kws{N}` и `kws{N}-1` (для media — наоборот).

**Откат** срабатывает, если WebSocket недоступен, DC не определён или соединение не похоже на
MTProto. Прочитанные у клиента байты повторяются дословно, затем поток просто перекачивается в обе
стороны. Куда именно уйдёт откат, решает опция **метка для остального трафика** (см. ниже).

### Защита от сбоев

| Что | Как ведёт себя демон |
|---|---|
| Все домены дата-центра ответили перенаправлением | дата-центр больше не пробуется до перезапуска |
| Любой другой сбой WebSocket (таймаут, ошибка) | дата-центр на паузе 60 секунд, затем пробуется снова |
| Пауза дата-центра, но **прямой путь к адресу только что не сработал** | пауза игнорируется и WebSocket пробуется снова: отдавать дата-центр заведомо мёртвому пути незачем |
| Прямая попытка к адресу провалилась | в течение 60 секунд новые соединения к нему закрываются **сразу**, а не ждут таймаут |
| Таймаут на первом домене | пробуется следующий домен того же дата-центра |
| Клиент подключился и молчит | соединение закрывается по таймауту приветствия (10 секунд) |
| Соединение пришло не через перенаправление | закрывается: иначе откат дозванивался бы до самого демона по кругу |
| Порт назначения не 80, 443, 5222 | закрывается: перехват такого не присылает |

Таймауты: открытие WebSocket 4 секунды, прямое соединение 5 секунд.

## Совместная работа с TrustTunnel

Пакет самостоятельный и работает без [TrustTunnel](https://github.com/NooBiToo/TrustTunnelOpenWrt),
но два пакета на одном роутере согласованы.

- **Сокеты демона** помечены `0x7467`. TrustTunnel (начиная с **1.0.14**) возвращает такой трафик без
  маркировки в туннель, поэтому при включённом «Трафик роутера через VPN» WebSocket-соединения
  демона всё равно идут напрямую.
- Если в списках TrustTunnel выбран **Telegram**, перехват `tgws` срабатывает раньше, и этот трафик в
  туннель не попадёт. Диагностика предупредит об этом.
- Что **нельзя** провести через WebSocket (веб-страницы Telegram, дата-центры 1, 3 и 5 на сети, где
  для них нет достижимого WebSocket-адреса, HTTP-транспорт), по умолчанию идёт **напрямую**. Если
  прямой доступ закрыт, этого трафика не будет. Для таких сетей есть опция **метка для остального
  трафика**: введите `0x9527` (метка туннеля TrustTunnel), и такие соединения демон отправит через
  туннель, как и до включения `tgws`. Без TrustTunnel опция не нужна.

Типичная схема для сети, где прямой доступ к Telegram закрыт:

1. Уберите Telegram из списков TrustTunnel (иначе WebSocket-трафик не получит ускорения).
2. Включите `tgws`.
3. Задайте метку `0x9527` во вкладке **Остальной трафик**.

Результат: сообщения и медиа идут через WebSocket напрямую, всё остальное — через туннель.

> Если после удаления списка Telegram из TrustTunnel его подсети остаются в маршрутизации, значит у
> вас версия TrustTunnel старше 1.0.14: в ней убранные подсети переносились через перезагрузку
> настроек. Обновите пакет или перезапустите службу TrustTunnel.

## Настройка без интерфейса

```sh
# Включить
uci set tgws.main.enabled='1'

# Цели WebSocket (по умолчанию DC2 и DC4), либо none — без WebSocket
uci set tgws.main.dc_ip='2:149.154.167.220,4:149.154.167.220'

# Остальной трафик Telegram через туннель TrustTunnel
uci set tgws.main.fallback_mark='0x9527'

# Вручную привязать новый адрес к дата-центру
uci set tgws.main.ip_dc='149.154.167.35:2'

# Свои интерфейсы локальной сети (по умолчанию устройство сети lan)
uci set tgws.main.lan_devices='br-lan br-guest'

uci commit tgws
/etc/init.d/tgws restart
```

Управление службой:

```sh
/etc/init.d/tgws start | stop | restart
/etc/init.d/tgws update_subnets     # обновить список подсетей и перезагрузить правила
/etc/init.d/tgws enable             # запуск при загрузке (пакет делает это при установке)
```

Проверка связи с Telegram из консоли (тот же запрос, что и на странице «Диагностика»):

```sh
tgws -probe -dc 2           # результат — JSON по каждому домену
tgws -probe -dc 4 -media
```

Полный справочник параметров — в [SETTINGS.ru.md](SETTINGS.ru.md).

## Диагностика и частые проблемы

Сначала откройте **Службы → Telegram → Диагностика** и нажмите **Запустить проверки**: там
подсказка к каждой проблеме. Из консоли:

```sh
logread -e tgws                  # журнал демона и init-скрипта
nft list table inet tgws         # загружены ли правила перехвата
cat /var/run/tgws.json           # счётчики, адреса без известного дата-центра
/etc/init.d/tgws running && echo работает
```

Подробный журнал по каждому соединению включается флагом `-v`: временно запустите демон вручную
(`tgws -v -listen :5454 -stats /tmp/tgws.json`) на другом порту.

| Симптом | Что проверить |
|---|---|
| Telegram не стал быстрее | Диагностика: правила перехвата загружены? В **состоянии** растёт «Через WebSocket»? Если растёт «Пропущено напрямую» — клиенты не доходят до WebSocket |
| Счётчик «Через WebSocket» не растёт совсем | Устройство использует **прокси** (MTProxy, SOCKS5) или **VPN**: такой трафик в перехват не попадает. Отключите прокси в настройках Telegram |
| Не грузятся фото и видео | Оставьте в «Цели WebSocket» только `4:149.154.167.220` или введите `none` |
| Не подключается только гостевая сеть | Зона файрвола гостевой сети не принимает входящий трафик (`input reject`): fw4 отклоняет перенаправленные соединения. Нужна зона с `input ACCEPT` |
| Перехват пропал после остановки файрвола | `/etc/init.d/firewall stop` снимает все таблицы. Выполните `/etc/init.d/tgws restart` |
| В «состоянии» есть адреса без известного дата-центра | Демон определяет их перебором сам. Если список не пустеет, добавьте адрес вручную в «Ручное соответствие» |
| Веб-страницы Telegram (`t.me`, превью, мини-приложения) не открываются | Это не MTProto, WebSocket его не проведёт. Задайте метку туннеля (см. выше) |
| Подключение к Telegram долгое | В диагностике смотрите замечания по WebSocket: если первый домен дата-центра не отвечает, соединение ждёт его таймаут (4 секунды) |
| Служба не запускается, в журнале `dc_ip`, `ip_dc` или `fallback_mark` | Значение не прошло проверку демона (`tgws -check`): исправьте его |
| Диагностика пишет «Telegram не отвечает» только иногда | Провайдер может ограничивать частые соединения к одному адресу: повторите проверку позже, по одной |

**Адреса `149.154.167.220` недоступны вовсе.** Тогда WebSocket не откроется ни для одного дата-центра,
а пакет сможет только пропускать трафик напрямую. Проверьте в диагностике «Telegram отвечает по
WebSocket». Можно задать другой адрес целей, если вы знаете рабочий: `2:IP,4:IP`.

## Ограничения

- **Только IPv4.** Если на роутере включён IPv6, клиент может подключиться к Telegram по IPv6 и
  обойти ускорение. Отключение IPv6 в локальной сети делает ускорение полным (диагностика
  предупредит).
- **WebSocket по умолчанию только для DC2 и DC4**, потому что единственный известный публично
  адрес (`149.154.167.220`) обслуживает именно их. Остальные дата-центры идут напрямую или через
  метку.
- **Звонки и другой не-TCP трафик Telegram** не затрагиваются.
- **Клиенты с прокси или VPN** в перехват не попадают.
- **Определение дата-центра по адресам** опирается на короткую таблицу, ручное соответствие и перебор
  (см. выше). Новый адрес для нового клиента может быть «выучен» по первому ответившему
  дата-центру.
- **Не-MTProto трафик** на адреса Telegram (веб, HTTP-транспорт) WebSocket провести не может.
- **Провайдер может ограничивать** частые соединения к `149.154.167.220`: первое соединение иногда
  не проходит, а следующий домен проходит. Демон учитывает это, но задержка возможна.
- **Гостевые и прочие сети** нужно добавить в «Интерфейсы локальной сети», и их зоны фаервола
  должны принимать входящий трафик.
- Проверено на Android и Windows Desktop. **iOS не проверялся.**
- Это интеграция сообщества, а не официальный продукт Telegram.

## Обновление

Повторно запустите установку: она обновит пакет и демон, сохранив настройки.

```sh
sh -c "$(wget -O - https://raw.githubusercontent.com/NooBiToo/tgws-openwrt/main/install.sh)"
```

Страница «Состояние» показывает установленную и доступную версии. Файл `/etc/config/tgws`
защищён от перезаписи при обновлении.

## Удаление

```sh
# Остановить и выключить службу (снимает и правила перехвата)
/etc/init.d/tgws stop
/etc/init.d/tgws disable

# Удалить пакеты. Языковой пакет — в том же вызове: он зависит от основного
apk del luci-app-tgws luci-i18n-tgws-ru

# Убрать бинарник, скачанные списки и настройки
rm -f /usr/bin/tgws
rm -rf /etc/tgws /etc/config/tgws

# Убрать задание cron
sed -i '/tgws update_subnets/d' /etc/crontabs/root
/etc/init.d/cron restart
```

## Для разработчиков

Демон написан на Go (только стандартная библиотека, зависимостей нет). Каталоги:

- `cmd/tgws` — точка входа, флаги, проводка;
- `internal/proxy` — приём соединений, выбор дата-центра, откат, мост, счётчики;
- `internal/mtproto` — заголовок obfuscated2, AES-CTR, разбиение на пакеты;
- `internal/ws` — клиент WebSocket без `net/http` (экономит около мегабайта);
- `internal/dcmap`, `internal/origdst`, `internal/sockmark`, `internal/probe` — таблица дата-центров,
  `SO_ORIGINAL_DST`, `SO_MARK`, проверка связи;
- `packages/luci-app-tgws` — пакет LuCI: init-скрипт, генератор правил, бэкенд rpcd на ucode, страницы
  интерфейса, перевод;
- `tests` — тесты скриптов в POSIX sh.

```sh
sh scripts/test.sh -race ./...   # Go-тесты (без установленного Go — в контейнере golang)
sh tests/run.sh                  # тесты шелл-скриптов
sh scripts/build.sh dist         # бинарники под все архитектуры, с контролем размера
```

Непрерывная интеграция (GitHub Actions) на каждый push и pull request:

- `go vet`, `go test -race`, кросс-сборка под пять архитектур с ограничением размера;
- биты исполнения скриптов в индексе git (на Windows они по умолчанию теряются);
- тесты скриптов, `shellcheck` (версия закреплена), синтаксис init-скрипта;
- JSON, синтаксис и подключение модулей страниц LuCI, импорты и синтаксис бэкенда на ucode.

Релиз собирается по тегу `vX.Y.Z`: бинарники под пять архитектур, пакет и перевод через OpenWrt SDK.
Версия `PKG_VERSION` в `packages/luci-app-tgws/Makefile` обязана совпадать с тегом.
